Backups are taken with [rustic](https://rustic.cli.rs/), encrypted with a key
derived per repository, and written to a destination you own.

## Destinations

| Type | Where it writes |
| --- | --- |
| `s3` | Object storage: bucket, region, endpoint and prefix |
| `local` | A filesystem path on the host |
| `sftp` | A remote host over SSH |
| `azblob` | An Azure Blob Storage container |
| `gcs` | A Google Cloud Storage bucket |

<Callout type="warn" title="SFTP is key-auth only">
  The SFTP backend authenticates with an SSH private key. A destination
  configured with a password is rejected with that reason up front, rather than
  failing later mid-run.
</Callout>

Credentials for a destination are stored encrypted and decrypted only when a
run needs them.

## What can be backed up

| Source | How |
| --- | --- |
| Managed database | A logical dump of PostgreSQL, MariaDB or MongoDB; use a volume backup for Redis or ClickHouse |
| Compose database service | A logical dump of a recognised PostgreSQL, MariaDB/MySQL or MongoDB service inside a compose stack |
| Docker volume | A named volume, tarred through a helper container |

The source picker offers both databases and the live volume inventory from the
daemon, including orphans, so a volume whose owning resource is gone can still
be captured before you delete it.

## Schedules and retention

Runs are cron-scheduled. `keepLast`, `keepHourly`, `keepDaily`, `keepWeekly`,
`keepMonthly` and `keepYearly` retain the newest snapshots overall or by time
bucket within each repository. `retentionDays` sets a maximum age, and
`maxStorageGb` applies a schedule-wide stored-size ceiling after those rules.

The scheduler scans the schedule table **every minute** and the database is the
source of truth, so an edited cron expression or retention rule takes effect
on the next scan: there is no repeatable job to re-register.

```bash
otterdeploy backups list
otterdeploy backups run primary --destination bakdest_123
otterdeploy backups restore bak_abc123 --confirm primary
```

## Running one now

"Back up now" enqueues the same engine a schedule would, against a source you
pick. The run is recorded with no schedule attached, so manual runs stay
distinguishable from scheduled ones in the history.

## Reading a run

Every run keeps its own log lines across three streams: `stdout`, `stderr` and
`system`. Expanding a run in the dashboard reads them on demand. There is no
preview stub, so an empty log means the run genuinely produced no output.

Status values are real states, not a spinner: a run that failed says so and
keeps the output that explains why.

## Restore

Logical PostgreSQL, MariaDB and MongoDB dumps can be restored into a running
database. A volume snapshot can be restored only when no container, including
a stopped one, mounts that volume. Both modes overwrite the target. A physical
PostgreSQL backup cannot be restored in place: download its tar and extract it
into a fresh data directory with the server stopped.

Read the restore run afterwards rather than assuming a clean exit.

<Callout title="Practise it">
  A backup you have never restored is a hypothesis. Restore into a throwaway
  resource at least once before you need to do it under pressure.
</Callout>

## Encryption

Run and schedule records expose an encryption policy of `aes-256-gcm` (the
default) or `none`. Independently of that recorded value, the current backend
always gives Rustic a repository password: a deterministic 32-byte value
derived with HKDF-SHA256 from the install's master secret and the repository's
password domain. That domain contains the resource id or volume scope under an
external destination's prefix, and is organisation-qualified for managed
storage. Different sources sharing one destination therefore do not share a
password.
