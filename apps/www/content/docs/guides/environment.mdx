Environment variables are set per resource and resolved at deploy time. Keys
are `UPPER_SNAKE`; anything else fails validation.

```bash
otterdeploy env list --service web
otterdeploy env set API_URL=https://api.example.com --service web
otterdeploy env unset API_URL --service web
```

## References

A value can point at something else instead of copying it. Platform references
use double braces and resolve server-side for each deployment, so nothing has
to be updated by hand when the thing it points at changes.

| Reference | Resolves to |
| --- | --- |
| `${{<database>.DATABASE_URL}}` | A database's internal connection URL |
| `${{<database>.PGHOST}}` and other `PG*` exports | Individual database connection fields |
| `${{<service>.HOST}}`, `.PORT` or `.URL` | Another service's internal address |
| `${{<service>.<KEY>}}` | Another service's resolved environment variable |
| `${{project.<KEY>}}` | A shared project variable |
| `${{vault.<provider>.<ref>}}` | A value fetched from an external secret provider at deploy time |

References interpolate mid-string, so you can build a value out of parts:

```json
{
  "DATABASE_URL": "postgres://${{primary.PGUSER}}:${{primary.PGPASSWORD}}@${{primary.PGHOST}}:${{primary.PGPORT}}/${{primary.PGDATABASE}}"
}
```

Manifest env maps additionally accept apply-time references such as
`${database:primary.url}`, `${database:primary.host}` and
`${service:api.host}`. Their grammar is checked during manifest validation and
their values are substituted when the manifest is applied. Use the double-brace
platform form when a reference must be evaluated again for every deployment.

### Why references matter

The lookup is by resource **name**, late-bound at deploy. That is the mechanism
behind [previews](/docs/guides/previews): a preview that owns its own database
copy (also named `postgres`) resolves the same
`${{postgres.DATABASE_URL}}` to the copy. The manifest doesn't change.
Nothing is templated per environment.

## Sealed variables

A sealed value can be written and used by a deploy, but never read back out
through the API. The read path masks it, not just in the dashboard, but at the
RPC boundary, so neither you nor a stolen token can retrieve it after it's
set.

Use this for the secrets that would be expensive to rotate. Use a normal secret
variable when you'd rather be able to check what's in it.

Secrets are encrypted at rest under per-domain keys, with rotation support, so
rotating one class of secret doesn't mean re-encrypting everything.

## Environments

Named contexts (development, staging, production) whose overrides deep-merge
onto the project's base manifest:

```json
{
  "services": {
    "web": { "env": { "LOG_LEVEL": "info" } }
  },
  "environments": {
    "staging": {
      "services": { "web": { "env": { "LOG_LEVEL": "debug" } } }
    }
  }
}
```

Deploying `staging` gives `web` a `LOG_LEVEL` of `debug` and leaves every other
variable inherited. You maintain one manifest, not one per environment.

```bash
otterdeploy environments list
```

## When the manifest owns env

<Callout type="warn" title="A declared env map is authoritative">
  When a service declares a non-empty `env` map, `otterdeploy sync` reconciles
  its manifest-managed variables to that map. Omitting `env`, or declaring an
  empty map, leaves its variables under live control instead. Service mounts
  are always live-managed and survive a manifest apply.
</Callout>

Live variable edits are copied back into the server's saved manifest when that
manifest already declares the service's environment. They do not rewrite your
local file. Use `otterdeploy pull` to replace the local file with the saved
manifest before you sync:

```bash
otterdeploy pull          # replace the local config with the saved manifest
otterdeploy sync          # show the diff, then apply it
```
