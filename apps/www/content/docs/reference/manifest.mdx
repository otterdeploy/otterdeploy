A project can be described by one JSON document. Diff it, review it, commit it,
apply it.

```bash
otterdeploy pull          # replace the local config with the saved manifest
otterdeploy sync          # show the diff, then apply it
otterdeploy export        # render the project as a docker-compose stack
```

## Top level

```json
{
  "version": 1,
  "project": "storefront",
  "services": {},
  "databases": {},
  "composes": {},
  "environments": {}
}
```

| Key | |
| --- | --- |
| `$schema` | Optional. Points at the JSON Schema for editor completion |
| `version` | Schema version. Currently `1` |
| `project` | Project slug *(required)* |
| `services` | Named map of services |
| `databases` | Named map of databases |
| `composes` | Named map of compose stacks |
| `environments` | Named overrides that deep-merge onto the base |

Services and databases are **maps keyed by name**, not arrays. The name is what
[references](/docs/guides/environment#references) resolve against, so renaming
a key is a rename of the resource.

## Services

Discriminated by `source`.

### `source: "git"`

```json
{
  "web": {
    "source": "git",
    "repo": "acme/storefront",
    "branch": "main",
    "sourceSubdir": "apps/web",
    "build": { "builder": "auto" },
    "ports": [{ "container": 3000, "primary": true }],
    "env": { "DATABASE_URL": "${database:postgres.url}" }
  }
}
```

| Field | |
| --- | --- |
| `repo` | `"owner/name"`. Resolved against the org's installations on apply, so no opaque id lands on disk |
| `branch` | Branch whose pushes deploy this service. Falls back to the repo default |
| `sourceSubdir` | Repo-relative subdirectory: the monorepo case |
| `build` | Build configuration, below |

A git service may be staged unbound; only its build fails, clearly, until a
repo is attached.

### `source: "image"` and `source: "upload"`

`image` pulls a pre-built image. `upload` marks the service as upload-sourced;
the artefact is supplied out of band.

### Build configuration

Discriminated by `builder`. Every variant accepts `watchPatterns`, globs
against the changed paths in a push. When set, a push only redeploys if at
least one path matches; when unset, every push redeploys.

| Builder | Fields |
| --- | --- |
| `auto` | None. Inspects the repo: a Dockerfile means `dockerfile`, otherwise `railpack` |
| `dockerfile` | `dockerfilePath` (default `./Dockerfile`), `dockerfileContext`, `buildArgs` |
| `railpack` | `buildCommand`, `spa`, `staticRoot`, `packageManager`, `buildRunner`, `turboFilter`, `turboRemoteCache`, `turboPrune` |
| `compose` | `composePath` (default `./docker-compose.yml`) |

<Callout type="warn" title="buildArgs are not secrets">
  `--build-arg` values land in the image history. Use an
  [environment variable](/docs/guides/environment) for anything sensitive.
</Callout>

### Monorepos

A service in a monorepo sets `sourceSubdir` to its app folder. When the repo
root declares a workspace (`workspaces` in `package.json`, or
`pnpm-workspace.yaml`), the build runs from the **repository root** so the
lockfile, the workspace catalog, and the sibling packages the app imports all
resolve.

Turborepo is a task runner *over* that workspace, never a replacement for it.
When the root has both a `turbo.json` and a `turbo` dependency, the app is
built with `turbo run build --filter=<package name>`, which builds the internal
packages it depends on first. Without turbo, the app's own `build` script runs
on its own.

| Field | |
| --- | --- |
| `buildRunner` | `auto` (default), `turbo`, or `script`. `turbo` fails the build if turbo isn't usable, rather than quietly falling back |
| `turboFilter` | Overrides the derived `--filter`. Rarely needed |
| `turboRemoteCache` | Opt into Turborepo Remote Cache. Reads `TURBO_TOKEN` (plus `TURBO_TEAM` / `TURBO_API`) from the service's variables and passes them to the build as secrets, never as build args |
| `turboPrune` | Build from a `turbo prune`d copy of the workspace. See below |

#### Pruning the workspace

`turboPrune` builds from a copy of the monorepo containing only the packages
your app actually reaches. Measured on this repo, building `apps/server`:

| | Full | Pruned |
| --- | --- | --- |
| Build context | 48.9 MB / 3061 files | 23 MB / 1150 files |
| Packages installed | 17 | 10 |

The narrower install is the point — a backend service stops installing the
frontend toolchains of apps it never imports. It does **not** improve
install-layer caching: the build already copies only workspace manifests and
the lockfile before installing, so a source-only change never re-runs install.

It is off by default because `turbo prune` keeps only the root `package.json`,
the lockfile and `turbo.json`, and drops every other root-level file. A repo
whose packages do `"extends": "../../tsconfig.json"`, or that keeps a root
`.npmrc`, `patches/`, or shared tool config, would break. Otterdeploy checks
for those known hazards before using a pruned tree and silently builds the full
workspace instead when it finds one. The guard is conservative, not exhaustive:
if a build reads an unusual root-level script or config, disable `turboPrune`
and build the full workspace.

<Callout title="Uses the builder's turbo, not your repo's">
  Pruning runs before install, so it can't use the `turbo` in your
  `node_modules`. The builder image ships its own. On a self-hosted builder
  without it, the build logs a line and proceeds unpruned.
</Callout>

For the `dockerfile` builder, where the Dockerfile *lives* and what it is
*built with* are separate questions. A monorepo Dockerfile sits in the app's
subdirectory but COPYs the root lockfile and sibling packages, so it needs the
repository root as its build context:

| `dockerfileContext` | |
| --- | --- |
| `auto` (default) | Reads the Dockerfile's COPY sources and uses the repository root only when they require it |
| `subdir` | Always build from `sourceSubdir` |
| `root` | Always build from the repository root |

### Build caches

Three independent layers, none of which can fail a build:

- **Image layer cache** — always on, per image repository, on the build host.
- **Turborepo local cache** — mounted into the build so turbo restores
  unchanged packages even when the layer cache misses.
- **Turborepo Remote Cache** — opt-in via `turboRemoteCache`, shared across
  hosts.

To rebuild without any of them, use **Redeploy without cache** on the service.
It is a per-deploy choice rather than a setting: it drops the layer-cache
import (while still repopulating it for next time) and sets `TURBO_FORCE` so
turbo re-runs every task.

### Common service fields

| Field | |
| --- | --- |
| `replicas` | Task count |
| `ports` | `{ container, protocol?, appProtocol?, primary?, name? }` |
| `env` | `UPPER_SNAKE` keys; values may contain references |
| `startCommand` | **Exec form**: `["bun", "run", "start"]`, not a string |
| `entrypoint` | Exec form |
| `healthcheck` | `{ cmd, intervalMs?, timeoutMs?, retries?, startMs? }` |
| `resources` | `cpuLimit`, `memoryMb`, `cpuReservation`, `memoryReservationMb`, `diskMb`, `swapMb`, `pidsLimit` |
| `restart` | `{ condition: "none" \| "on-failure" \| "any", maxAttempts?, delayMs?, windowMs? }` |
| `preDeploy` | Hooks run after build, before new replicas take traffic: migrations |
| `postDeploy` | Hooks run after the new task reaches `running`: warmup, smoke checks |
| `domains` | Create-time seed only; see below |

<Callout title="Shell expressions need a shell">
  `startCommand` and the hooks are exec-form arrays. To run a shell expression,
  wrap it yourself: `["sh", "-c", "x && y"]`.
</Callout>

`domains` is a **create-time seed**, so an operator can set a domain before the
first deploy. After creation, domains are managed on the resource and this
field is deliberately not diffed for drift, otherwise applying the manifest
would undo every domain added since.

## Databases

Discriminated by `engine`. Each engine accepts only its own fields; unknown
engine-specific keys are rejected.

```json
{
  "postgres": { "engine": "postgres", "version": "17" },
  "cache": { "engine": "redis" }
}
```

Engines: `postgres`, `redis`, `mariadb`, `mongodb`, `clickhouse`.

## Environments

Overrides that deep-merge onto the base:

```json
{
  "environments": {
    "staging": {
      "services": { "web": { "env": { "LOG_LEVEL": "debug" } } }
    }
  }
}
```

<Callout title="Compose stacks aren't per-environment">
  `environments` blocks carry no `composes` key. A stack is an atomic unit in
  v1, not a per-environment tunable.
</Callout>

## What apply owns

Applying the manifest reconciles the resources it describes. Two things behave
differently and are worth committing to memory:

- **A non-empty service `env` map is owned by the manifest.** Omitting it, or
  declaring `{}`, leaves that service's variables under live control.
- **Service mounts are not.** Apply never touches them, so a volume added by
  hand survives.

Run `otterdeploy pull` before a sync when you want to replace the local file
with the server's saved manifest.
