Why

Two things are wrong in the environment switcher today. The graph shows the same resources whichever environment is selected, and the “main” environment behaves as though it were the last one added.

The second was a genuine defect, and is fixed, it shipped as P0. The header nav resolved the default environment by string-matching the slug "production" and falling back to environments[0] from a live query with no .orderBy(), while ignoring project.environmentId, the main-environment pointer that already existed in the schema. variables.tsx:52 ran the same query with an explicit sort and commented that “the collection isn't intrinsically ordered”; the header nav was the one place that omitted it. Resolution is now authority-first, pointer, then the production convention, then a deterministically sorted first row: in features/shell/environment-default.ts, with thirteen tests whose load-bearing assertions are about order independence: the same set in a different sequence must resolve identically, and a new environment arriving at the front of the list must not change the answer.

The first is not a defect. It is the absence of a feature. No resource table carries an environmentId; only project, serviceEnvVar and projectEnvVar do. Environments name a variable scope. The switcher sits in the global breadcrumb and so implies a filter it never applies.

That scoping existed once and was deliberately removed. PR #31 (3678b0f3, “previews are resources, not environments”) moved previews out of the environment table because the env-as-scope model copied every database per pull request, and produced four concrete failures: unscoped teardown destroying other repos' same-numbered previews, closed PRs leaking containers and volumes, preview migrations running against production databases, and preview builds superseding production's running deployment row. What remains, environment as a variable scope with a 1:1 project pointer. Is the residue of that retreat, which is also why the switcher looks like it should filter.

This plan re-introduces scoping for long-lived, operator-managed environments, reusing the preview mechanism that survived rather than the model that was rolled back.

The model

A resource row carries an optional scope. Resolution prefers the narrowest scope that owns a row and falls back outward, so an environment or a preview owns only what it actually overrides. This is what keeps a pull request costing one container and one route by default instead of a copy of every database in the project.

preview postgres preview_id set. A branch this PR owns
↓ no row: fall outward
environment postgres environment_id set. Staging's own database
↓ no row: fall outward
base postgres both null: the project's original resource

Because references are late-bound by resource name. DATABASE_URL = ${{postgres.DATABASE_URL}} resolves at deploy time, the same manifest produces different wiring per scope with no user-authored change. That property already exists in lib/variables/resolver.ts; this plan widens it from two levels to three.

Schema delta

resource
  + environment_id  text  null  → environment.id
    preview_id      text  null  → preview.id        (exists)

preview
  + base_environment_id  text  → environment.id

preview.base_environment_id is what makes the intended mental model true: a pull request into the branch that staging deploys produces a preview of staging, and its database branch copies that environment's data. Today every preview branches from production because there is nothing else it could branch from.

Mirroring, staging does not drift

Staging follows production. A change to production reaches staging too, and staging only differs where the operator has deliberately made it differ. That is a standing relationship, not a copy taken once at creation.

This is already the manifest's design, and it is already wired. The manifest carries a top-level environments.<name> overlay that deep-merges onto the base, and resolveEnvironment (stack/manifest/merge.ts) implements exactly the semantics above. Both manifest.diff and manifest.apply already call it with the target environment (router-manifest.ts:78,127,206), and seven tests pin the rules, including “inherits unchanged when the env block is missing”, which is mirroring stated as a test.

So the override mechanism does not need designing. The merge rules are settled and tested:

In the overlay Result
Key absent Inherits base unchanged: this is what “mirrors” means
Scalar present Replaces the base value
Object present Deep-merged, recursively
Array present Replaces wholesale, no per-element merge
Value is null Deletes the key from the base
Discriminator differs (source / engine) The override replaces the whole block; no cross-discriminator merge

What is actually missing is narrower than it first appears: apply resolves the manifest per environment, but the resources it writes to are not environment-scoped, so a staging apply lands on production's rows. Scoping the write target is the work, not building an override system.

One consequence to decide deliberately: when production changes, staging should not silently reconcile underneath a running system. The safe shape is that propagation lands in staging as a pending change on the existing pending-changes bar, and the operator deploys it: the same path every other manifest edit already takes. That keeps “we should be able to change it on staging as well” true without turning a production edit into an unattended staging deploy.

The silent fallback is the highest-severity defect in the system today. branchOne deletes the branch resource when the copy fails so a retry is possible (git/preview-db.ts:277), and branchProjectDatabases is best-effort per database. Between the failure and a retry the preview has no scoped row, so name-based resolution finds the base, and the preview's migrations and writes land on production data. On swarm this is not a window but a permanent condition, because branchDatabase throws. The fix is not better logging; it is that a preview with a required branch must not reach a running state without it.

Copy-on-write branching

The target is Neon's branching model: a branch is instant, shares blocks with its origin until written to, and is cheap enough that every open pull request can have one. On self-hosted Postgres in a container, the mechanism that gives that is a filesystem-level snapshot and clone of PGDATA: zfs snapshot followed by zfs clone.

The seam for it already exists and is already specified. SnapshotDriver has branch() / destroy() / probe(), and the copy driver's own docstring states the intended asymmetry: “zfs clones the raw PGDATA volume at the volume layer, before the branch container boots”: whereas copy must dump and restore a layer up, with both containers running. Implementing the driver is the work; designing the interface is not.

What copy-on-write actually needs, beyond the driver itself:

Requirement Why it is not just a driver
PGDATA must live on a ZFS dataset Databases today get a plain Docker named volume (otterdeploy-pgdata-<project>-<resource>, view-helpers.ts:79). A volume that is not on ZFS cannot be cloned, so provisioning has to create a dataset per database and bind it. A change to database creation, not only to branching.
Existing databases cannot be branched instantly Anything created before the change sits on a plain volume. It keeps working and keeps using copy; moving it to ZFS is a data migration nobody should be forced into.
Driver selection becomes per-database resolveSnapshotDriver() is called once for the whole batch (preview-db.ts:144). With mixed hosts (some databases on ZFS, some not) it has to resolve per base database instead.
Snapshot consistency A ZFS snapshot of a running Postgres is crash-consistent; the clone replays WAL on first boot. Acceptable, and the same guarantee a power cut gives, but issue a CHECKPOINT first so recovery is short rather than arbitrary.
A clone pins its origin snapshot ZFS will not destroy a snapshot that a clone depends on. See below. This is the teardown hazard the copy path does not have.

Where ZFS gets provisioned

The installer. scripts/install.sh is already the one place that touches the host as root: it installs packages across the debian, rhel and arch families, installs Docker, and writes the compose stack. Adding ZFS packages and creating the dataset root belongs there, not in the application, which never has host privileges and cannot create a pool.

The control-plane database is not a branch source. install.sh provisions otterdeploy's own Postgres. postgres:17-alpine on the otterdeploy-postgres-data named volume, pinned to 17 because 18+ rejects the data mount. That is the platform's internal database: it holds projects, resources and deployments, it is never referenced by a ${{…}} ref, and it must never be snapshotted for a preview. User databases are a different thing entirely, created by the runtime driver as otterdeploy-pgdata-<project>-<resource>. Only those are branch sources, and only those move onto datasets.

The installer can provision it, but what it can provision depends on the host, and that determines what an operator actually gets:

Host Result
Spare block device A real pool. Instant branching with no meaningful overhead: the intended configuration.
No spare device, ZFS module available A file-backed vdev on the existing filesystem. Copy-on-write semantics are intact and branching is still instant, at some I/O cost from the nesting. Acceptable for most self-hosters, and worth offering rather than refusing.
No ZFS kernel module Not possible at any level: some VPS kernels simply do not ship it. copy remains, previews stay expensive on large databases, and nothing breaks.

Two consequences for the rollout. Upgrading an existing install must never require ZFS. Every database already on a plain volume keeps working on copy, which is exactly why driver selection has to become per-database rather than per-host. And the installer's ZFS step is opt-in and skippable, because an operator who declines it should get a working platform with slower branching, not a failed install.

Preview limits and manual triggers

Two controls belong to the preview lifecycle rather than to branching, and both change what P3 has to build.

A cap on concurrent previews. This is already a known gap. pr-previews.md lists “per-project preview caps” as outstanding alongside COW itself. Idle teardown bounds how long a preview lives; nothing bounds how many exist, so a busy repository can open twenty pull requests and provision twenty databases. The cap is enforced at preview creation, and the decision that matters is what happens when it is hit: refuse the new preview and say so on the pull request, rather than evicting the oldest. Eviction would tear down a preview someone is actively reviewing to make room for one nobody has looked at yet. A refusal that names the cap is honest and actionable; a silent eviction is neither. The same rule as idle GC applies, never a silent cap.

An on-demand trigger. A repository with automatic previews turned off should still be able to ask for one, by commenting @otterdeploy preview on the pull request. Mechanically this is a new webhook path: the App currently subscribes to ["push", "pull_request"] only (git/manifest.ts:128), so issue_comment has to be added to the event list and the handler switch, then routed into the same provisioning job the pull_request path uses. Everything downstream (branch, build, route, comment, teardown) is unchanged.

A comment trigger is an authorization boundary, not a convenience. Anyone who can see a public repository can comment on its pull requests. Without an author check, @otterdeploy preview is an unauthenticated request to provision compute and clone a database on someone else's infrastructure. The trigger must verify the commenter's association with the repository (author_association, or an explicit permission lookup) before it does anything, and previews created this way still count against the cap: otherwise the cap is bypassable by anyone with a keyboard.
Adding an event has an operational cost worth planning for. Changing the GitHub App's subscribed events means every existing installation has to accept the updated permissions before the new trigger works for them. The feature ships dark for anyone who has not accepted, so the rollout needs to detect that state and say so rather than appearing broken.

Branching under Swarm

The swarm driver throws 501 today because both branch transports assume the database is on the control plane's own host. copy reaches it with a docker exec over the local socket (pgDumpToBuffer(docker, containerId, …), backups/copy.ts), and the ZFS path uses runOnHost, a privileged helper that nsenters PID 1 of whichever machine the control plane runs on. Under Swarm a database can be scheduled anywhere, so both reach the wrong machine.

The fix is placement, not new transports. Pin databases to the control-plane host and both mechanisms are correct again, unchanged. Three facts about how otterdeploy is installed make that hold:

Fact Consequence
The installer runs docker swarm init on the install host (install.sh:654) That machine is the manager, and it is where the platform already lives.
The control plane is a plain docker compose stack, not docker stack deploy. There is no deploy: or placement: block in docker-compose.prod.yml It is pinned to the install host by construction and cannot be rescheduled, even in a multi-manager cluster. The host runOnHost reaches is therefore stable.
The ZFS pool is provisioned on that same host (install.sh:914-974) Pinning databases there puts them on the machine that already has the pool. No pool-per-node, and no cross-node execution.

So Swarm needs no branching-specific work at all: services scale across the cluster, databases stay on the manager, and the 501 is deleted because the case it guarded against no longer occurs. placementServerId already exists and already means exactly this. A hard placement constraint for a resource whose volume does not move with it.

The one case this does not cover: a database pinned to a worker. Placement is operator-controlled, so someone can pin a database to a node that is not the control-plane host, and then neither transport can reach it. That is a configuration conflict, and it should surface where the conflict is created rather than as a failed branch hours later: refuse to enable preview branching on a database pinned off-host, and refuse to move a branch-enabled database off-host. If it does slip through, Blocked catches it, the preview refuses rather than falling back to production.

Making copy talk to the database over the overlay hostname instead of docker exec would lift that restriction entirely, since the overlay reaches every node. It is a genuine simplification and worth doing eventually, but it is no longer on the critical path: it buys off-host databases, not Swarm support.

Clone lifetimes

Under copy a branch is an ordinary independent volume, so destroying a base database is unaffected by any preview. Under ZFS it is not: every open preview's clone holds its origin snapshot alive, and ZFS refuses to destroy a snapshot, or the dataset holding it, while a clone depends on it. This is the one place where copy-on-write changes an operation that has nothing to do with previews, so it gets designed rather than discovered.

The bookkeeping this needs already exists. databaseResource carries branch_strategy and branch_snapshot_ref (schema/project.ts:363,366), and teardown already passes the stored ref back to the driver (preview-teardown.ts:114) rather than recomputing it: the same record-it-don't-recompute lesson as the preview slug. What is missing is the guard and the ordering.

Rule Where it goes, and why there
Deleting a base database refuses while live branches exist A precondition in resource-delete.ts, checked before anything is stripped, not a failure handler. Today the flow removes the database from the manifest first, on purpose, so that a partial teardown diffs as a recoverable delete rather than a phantom create. If the ZFS destroy is instead allowed to fail at step three, the manifest entry is already gone while the dataset is still on disk. The query is cheap: resources whose branched_from_resource_id is this database and whose preview_id is not null.
The refusal names the previews, and flags pinned ones Ordinarily this heals itself: previews are reaped at auto_teardown_at, so the block is temporary and waiting is a valid action. A pinned preview (auto_teardown_at NULL) never expires and pins the database indefinitely, so those must be named separately: they need a human, not patience.
Teardown destroys the clone before the snapshot Inside the zfs driver's destroy(). Reversing the order fails on the first call. Both steps must tolerate the object already being gone, because a teardown that dies between them otherwise leaves a snapshot that holds space and blocks the base delete permanently.
A failed branch teardown is recorded, not abandoned Reuse recordOrphanedResource / orphan-gc.ts, which already does exactly this for a service container whose daemon was unreachable. Without it, one failed teardown blocks base deletion forever with nothing tracking why.
Never zfs promote a preview clone Promotion would reparent the clone so the base becomes deletable, and it is the wrong answer here. It makes an ephemeral PR preview the origin holder of production's blocks, inverting the lifetime relationship: the short-lived thing now pins the long-lived one, and the preview cannot be torn down without another promotion. The operation exists; it is not for this.
The failure mode to design against is an operator who cannot act. “Delete this database” returning a filesystem error about dependent clones is unactionable, nothing in the UI connects a ZFS dataset to someone's open pull request. A refusal that says “3 preview branches depend on this database: PR 128, PR 131, PR 140 (pinned)” is an instruction. The rule is that the guard lives in the application layer, where preview identity is known, and the filesystem error is never the thing the operator sees.

Naming contract

Every scope must produce distinct container, volume, host and route names, and the base scope must keep its current names byte-for-byte, or every existing deployment is recreated on upgrade. 

export type Scope =
  | { kind: "base" }
  | { kind: "environment"; slug: string }
  | { kind: "preview"; slug: string; prNumber: number };

export function scopeSuffix(scope: Scope): string {
  switch (scope.kind) {
    case "base":        return "";              // ← load-bearing
    case "environment": return `-${scope.slug}`;
    case "preview":     return `-pr-${scope.prNumber}`;
  }
}
  • The empty string is load-bearing. Any suffix on base renames every running container on upgrade.
  • Environment slugs need a reserved list. An environment slugged pr-128 would collide with a preview suffix. Reject at create time.
  • Three partial unique indexes replace the current two: base (both null), environment (env set, preview null), preview (preview set). Existing rows have both columns null, so the base index still matches them unchanged.

Phases

Each phase is shippable alone and leaves the system consistent.

P0: Fix the default environment. (shipped) Resolve from project.environmentId, then slug production, then a deterministically sorted first row. Independent of everything else; ships now.

P1: Scope union and migration. (in progress) Generalize PreviewScope to Scope, with the main environment rendering as base so no running container is renamed; reserve slugs that would collide with a preview's generated name; add environment_id to resource with the three partial indexes. No backfill: see below.

P2: Environment-scoped resources and mirroring. Scope-aware resource lists, graph, reconcile and naming, so an apply resolved for staging writes to staging's rows. The overlay and merge already exist; this phase points the write target at the right scope and surfaces inherited changes on the pending-changes bar.

P3: Previews that are cheap and reliable. Shipped as one phase, because a preview that is trustworthy but expensive still will not get used. Durable provisioning: branching and teardown move out of the webhook into jobs keyed on (preview, sha), with the closing claim that makes teardown-vs-build deterministic and the Blocked state that stops a failed branch reaching production. Instant branching: ZFS-backed PGDATA on database creation, the copy-on-write driver behind the existing resolveSnapshotDriver seam, per-database driver selection so ZFS and non-ZFS databases coexist, and the clone-lifetime rules: delete guard, clone-before-snapshot teardown, orphan recording. copy stays as the fallback for every database not on a dataset. Runtime parity costs almost nothing: databases pin to the control-plane host, both existing transports are then correct under Swarm unchanged, and the 501 is deleted rather than documented.

There is no backfill, and that is a consequence of the naming rule. Because the main environment renders as base, “belongs to the main environment” and environment_id IS NULL are the same state. Every existing row is therefore already correct the moment the column is added, and the migration is purely additive: one nullable column, one narrowed partial index, two new indexes, and no UPDATE. The earlier concern: a partial backfill leaving the graph reading empty, indistinguishable from data loss: cannot occur because no rows are rewritten.

The one ordering detail that survives: the recreated base index is narrower than the one it replaces (preview_id is null becomes preview_id is null and environment_id is null), so it indexes a subset of the same rows. If the old index held, the new one holds. The drop-and-recreate cannot fail on pre-existing data. Reversing it still requires dropping the indexes before the column, or uniqueness is transiently violated mid-migration.

Verification

Typecheck and unit tests are necessary but not sufficient; the failures this plan targets are ordering and cleanup failures that only appear against a real runtime.

  • bun run typecheck and bun run test clean across the workspace.
  • Unit: scopeSuffix returns "" for base, assert byte-identical names against a fixture captured before the change.
  • Unit: resolver returns null rather than the base row when a required branch is missing.
  • Migration: run P1 against a restored production dump and assert every project's graph returns the same resource set as before, and that every pre-existing row still has environment_id IS NULL. The assertion is deliberately the inverse of what a backfill would want: nothing should have moved.
  • Naming, byte-identical: capture the container, volume and host names of a deployed project before migrating, and assert they are unchanged after. This is what the main-renders-as-base rule buys, and the only way to know it held.
  • End-to-end, environments: mirror production into staging, deploy, confirm distinct containers and volumes and that production is untouched.
  • End-to-end, previews: open a PR against a repo with an opted-in database; confirm the branch is a point-in-time copy of the base environment's data; push again and confirm the branch is reused; close and confirm containers, volumes and routes are gone while every base resource survives.
  • Fault injection: fill the disk on the target node so the branch copy fails; confirm the preview reports Blocked and no container starts against the production database.
  • Race: close a PR while its build is running; confirm no container exists afterwards.
  • Clone lifetime: with an open preview branched off it, attempt to delete the base database. Confirm the refusal names the PR, that the manifest entry and the dataset are both still intact afterwards, and that the same delete succeeds once the PR is closed.
  • Clone lifetime, pinned: pin the preview (auto_teardown_at NULL) and confirm the refusal calls it out as pinned rather than implying it will expire.
  • Clone lifetime, partial teardown: kill teardown between destroying the clone and destroying the snapshot; confirm a re-run completes rather than erroring on the missing clone, and that the orphan record is what drives the retry.

Resolved edges

Specifications leak at the joints, not in the middle. Each of these was underspecified enough that two people implementing it would have made different, both-defensible choices, which is the definition of a gap worth closing before code.

Gap Resolution
A preview is already Running and a new push's re-branch fails The running container keeps serving its existing branch (that data is still valid) and only the new rollout is withheld. Blocked applies to reaching a running state, not to leaving one. Tearing down a working review environment because a later branch failed is worse than the failure.
Cap scope, default, and whether pinning bypasses it Per project, defaulting from an instance setting alongside PREVIEW_IDLE_TEARDOWN_HOURS. Pinned previews count against it. Otherwise pinning is a silent bypass. Comment-triggered previews count too, for the same reason.
Which commenters may trigger a preview OWNER, MEMBER, COLLABORATOR: write access or better. CONTRIBUTOR and NONE are refused, so a drive-by commenter on a public repository cannot provision compute. A refusal reacts to the comment rather than replying, so the bot cannot be made to spam a thread.
How per-database driver selection knows the substrate Recorded on the base database at creation, not probed at branch time. A probe races with pool changes and would make branching non-deterministic. branchStrategy already exists on the branch row; the base needs the equivalent.
What creating a mirrored environment actually writes The environment row plus an empty environments.<slug> block. Apply already resolves per environment, so an empty overlay means “identical to base” with no special-casing: inheritance is the absence of an override, not a copy.
Deleting an environment that still owns running resources A typed confirmation naming exactly what will be destroyed, then resources and environment go together. Note this is deliberately looser than the database-delete guard, which refuses outright: a database is depended on by things outside its own scope, an environment is not.
P1 down-migration ordering Drop the three partial unique indexes before dropping the column, so uniqueness is never transiently violated mid-migration. Nulling the column alone is not a valid reverse.
Retention and rollback constrain each other, and neither plan owns it Assigned to whichever ships first: a retention count must mean “N rollback-capable deployments”, never “N rows”, because pruning an image silently destroys the rollback target that depends on it.

Decided

Mirroring is a standing relationship, not a copy. Staging follows production and only differs where the operator made it differ. Implemented as the manifest's environments.<name> overlay, which already exists, is already resolved by diff and apply, and is already tested.

Environments are uncapped. Operators self-host; the disk and the machine are theirs, and capping a count they are already paying for buys nothing.

A failed database branch blocks the preview. No container starts, the PR comment says why, and the retry is explicit. This is the fix for the silent fallback, a preview must never reach a running state bound to production data.

Branching works in Swarm too. The 501 goes away. A runtime an operator can select must not have a feature hole in it. Blocked stays as the guard for a branch that genuinely fails, but “you chose Swarm” is not a failure and must never be the reason a preview cannot branch.

An inherited change lands on staging's pending-changes bar. A production edit is never an unattended staging deploy: the change propagates as pending and the operator deploys it, on the same path every other manifest edit already takes. Staging still cannot drift, because the pending change sits there until applied.

Durable provisioning and instant branching ship together as P3. A preview that is trustworthy but expensive still will not get used, so copy-on-write moves up rather than trailing as a separate phase.

Status

No decisions. Every choice this plan depends on has been made, and the remaining unknown is a property of the hosts rather than of the design: whether a given machine can carry a ZFS pool at all. That is discovered by the installer at install time, not decided here, a host with no ZFS module gets copy and a working platform, and nothing in the plan waits on the answer.
